# LegendaryAI

LegendaryAI is a plain HTML/CSS/JS web app with account-based chat, conversation history, attachments, model routing, token quotas, and a Supabase Edge Function backend.

## Current production architecture

```text
Browser
  ↓
Supabase Auth
  ↓
Legendary Engine (Supabase Edge Function: ai-chat-v10)
  ↓
┌───────────────────────────────┐
│ Native Core                   │
│ Ollama-compatible local model │
│ Hugging Face Space (optional) │
└───────────────────────────────┘
  ↓
PostgreSQL / Storage
```

The browser does not receive model service credentials. Supabase service-role credentials and private inference credentials stay server-side.

## Important truth about AI availability

The repository contains an Ollama-compatible runtime path, but a **real self-hosted model is not currently configured in production**. The `LEGENDARY_LOCAL_AI_URL` secret is the required gateway boundary. The production model registry currently contains local-model profiles whose gateway is unavailable, so they must not be described as an already-running neural foundation model.

The Native Core is deterministic/orchestration code for bounded tasks; it is **not** a foundation model comparable to ChatGPT or Claude. Open-ended generation requires a configured model backend.

The health boundary is exposed by the `local-model-health` Edge Function. When `LEGENDARY_LOCAL_AI_URL` is absent or unreachable it returns `MODEL_UNAVAILABLE` rather than pretending that a model is ready.

## Security and data isolation

- Supabase Auth identifies the user before AI requests are processed.
- Conversation sync uses an authenticated RPC with an explicit user ownership guard and row locking.
- Browser conversation caches are namespaced by user identity by the cloud-sync layer.
- Chat attachment storage uses the private `chat-attachments` bucket and user-folder ownership policies.
- Model and payment secrets are kept in Supabase Edge Function secrets, never in browser JavaScript.
- `vercel.json` applies production security headers/CSP.

## Conversation sync

Conversation data is stored in PostgreSQL and mirrored locally for responsive UI. The production sync path uses `public.sync_conversation(...)` so conversation metadata and messages are reconciled atomically instead of repeatedly deleting and reinserting an entire account's history.

Conversation URLs use stable slugs where available. Message IDs generated by the current chat runtime use UUIDs when the browser supports `crypto.randomUUID()`.

## Attachments

The `chat-attachments` Storage bucket is private. Objects are expected under a user-specific first path segment, and storage policies restrict read/insert/delete operations to that owner.

Historical base64 image data is not intentionally carried through ordinary text-chat context when it is no longer needed.

## AI request reliability

The current runtime includes:

- bounded request payloads and context compaction;
- historical attachment stripping for normal text context;
- stable client-visible error codes such as `AUTH_REQUIRED`, `PAYLOAD_TOO_LARGE`, `TIMEOUT`, `RATE_LIMITED`, `MODEL_UNAVAILABLE`, `ENGINE_UNAVAILABLE`, and `NETWORK_ERROR`;
- token reservation/refund around configured model execution;
- model capability negotiation;
- local-model health checks;
- usage logging for successful model calls.

A remaining runtime hardening item is to make configured local-model failures fail closed instead of silently switching to Native Core for requests that explicitly require a model. Until that change is deployed, `fallbackUsed` must be treated as a real fallback signal rather than proof of model execution.

## Local model gateway

To run a real self-hosted model, provide a private Ollama-compatible gateway and configure the Supabase Edge Function secret:

```text
LEGENDARY_LOCAL_AI_URL=https://your-private-ollama-server
```

The gateway must expose the Ollama `/api/chat` contract and contain the model IDs selected in `public.ai_models`.

Do not put the gateway URL, bearer credentials, or service-role key in frontend JavaScript.

A production-ready rollout should verify all of the following before enabling a model profile:

1. `local-model-health` reports `ok: true` and lists the expected model.
2. An authenticated `ai-chat-v10` request reaches the gateway.
3. The response has non-empty model-generated text.
4. Token reservation/refund accounting remains correct.
5. A gateway timeout produces an explicit model-unavailable/timeout result instead of a fabricated answer.

## Supabase functions

Relevant Edge Functions include:

- `ai-chat-v10` — authenticated AI request boundary and model routing.
- `local-model-health` — private gateway readiness check.
- `owner-stats` / `owner-admin` — owner operations.
- `token-reset` — controlled token reset workflow.
- `momo-create-payment` / `momo-ipn` — payment integration.
- `image-generate` — paid image-generation integration; this is separate from zero-cost local text inference.

## Development

The project is intentionally a static frontend plus Supabase backend rather than a Node application. The `tests/` directory contains focused regression tests that can be run with a JavaScript runtime where applicable.

When changing production Edge Functions, verify the deployed function version and runtime logs after deployment. When changing SQL, use a migration and verify permissions/RLS after applying it.
